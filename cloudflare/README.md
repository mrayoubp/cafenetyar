# اجرای موقت روی Cloudflare Workers

این پیکربندی همان برنامهٔ اصلی را روی آدرس `workers.dev` اجرا می‌کند؛ دامنهٔ شخصی لازم نیست. برای APIهای پنل، مقاله‌ها و سامانه‌ها، دیتابیس D1 جداگانه می‌سازد. انتقال داده‌های زندهٔ میزبان قبلی انجام نمی‌شود. حسابداری و حساب‌های قدیمی همچنان به همان Convex قبلی متصل‌اند.

## انتشار از داشبورد Cloudflare

1. وارد https://dash.cloudflare.com شوید. در **Workers & Pages** گزینهٔ **Create application → Import a repository** را بزنید و GitHub را متصل کنید.
2. مخزن خصوصی `mrayoubp/cafenetyar` و شاخهٔ `main` را انتخاب کنید. نام Worker را **`cafenetyar-temp`** بگذارید. این پروژه **Worker** است؛ آن را به‌عنوان سایت استاتیک Pages وارد نکنید.
3. پوشهٔ ریشه را خالی یا `/` بگذارید. دستور Build را **`npm run setup`** و دستور Deploy را **`npm run cloudflare:deploy`** تنظیم کنید. متغیر Build با نام **`NODE_VERSION`** را **`24`** بگذارید و Deploy را بزنید.

Cloudflare باید به اسکریپت انتشار دسترسی **Workers Scripts: Edit** و **D1: Edit** بدهد. اگر توکن خودکار Workers Builds مجوز D1 نداشت، در تنظیمات Build یک API token محدود به همان حساب با این دو مجوز تنظیم کنید. توکن را فقط در قسمت Secret خود Cloudflare ثبت کنید؛ داخل چت یا گیت‌هاب نفرستید.

اسکریپت، دیتابیس `cafenetyar-temp` را فقط اگر وجود نداشته باشد می‌سازد، migrationها را قبل از انتشار اعمال می‌کند، سپس Worker را منتشر می‌کند. دیتابیس موجود پاک یا جایگزین نمی‌شود. آدرس واقعی بعد از موفقیت در داشبورد نمایش داده می‌شود؛ هیچ آدرس `workers.dev` از پیش در این راهنما فرض نشده است.

## ورود امن پنل مدیریت

ورود ChatGPT فقط روی میزبان Sites برقرار است. روی Cloudflare، ورود پنل از **Cloudflare Access** انجام می‌شود. تا قبل از تنظیم آن، صفحهٔ عمومی قابل انتشار است اما پنل مدیریت غیرفعال می‌ماند.

1. در **Cloudflare Zero Trust → Access → Applications** یک برنامهٔ **Self-hosted** برای مسیر **`<آدرس Worker>/manage*`** ایجاد کنید. در سیاست Allow، فعلاً فقط ایمیل مالک را مجاز کنید. مسیر `/api/` یا کل سایت عمومی را زیر این سیاست قرار ندهید. در دامنهٔ `workers.dev`، پشتیبانی مسیر Access را از داشبورد همان Worker بررسی کنید؛ اگر طرح یا تنظیمات حساب این مسیر را پشتیبانی نکرد، از یک زیردامنهٔ Cloudflare با همان مسیر استفاده کنید.
2. مقدار **Application Audience (AUD)** و دامنهٔ تیم مانند `your-team.cloudflareaccess.com` را از تنظیمات همان برنامه بردارید.
3. در **Worker → Settings → Variables and Secrets** این متغیرهای Runtime را تنظیم و دوباره Deploy کنید:

| نام | مقدار |
| --- | --- |
| `CF_ACCESS_TEAM_DOMAIN` | دامنهٔ واقعی تیم، بدون `https://` |
| `CF_ACCESS_AUD` | Audience همان برنامهٔ Access |
| `OWNER_EMAIL` | ایمیل دقیق مالک، مطابق حساب Access |
| `OWNER_PHONE` | شمارهٔ تماس مالک، فقط اطلاعات تماس |

در `/manage` وارد Access شوید، دکمهٔ ورود پنل را بزنید و تأیید دومرحله‌ای پنل را راه‌اندازی کنید. Worker امضای JWT، صادرکننده، Audience و انقضا را بررسی می‌کند؛ هدرهای هویت ارسال‌شده توسط کاربر پذیرفته نمی‌شوند. کوکی Access باید برای درخواست‌های همان دامنه، از جمله `/api/`، ارسال شود.

ایجاد حساب در D1 به‌تنهایی مجوز ورود Access ایجاد نمی‌کند. برای ادمین‌های بعدی، سیاست Access و مجوزهای داخل پنل هر دو باید تنظیم شوند. اطلاعات پنل و هویت‌های Sites قبلی به این دیتابیس منتقل نمی‌شوند.

## اجرا از ترمینال، در صورت نیاز

با Node.js 24 و npm، فقط در سیستم خود مالک اجرا کنید:

```sh
npm run setup
npx --yes wrangler@4.164.0 login
npm run cloudflare:deploy
```

برای بررسی بسته بدون انتشار:

```sh
npx --yes wrangler@4.164.0 deploy --dry-run
```

دستور `deploy` از تنظیمات `build` فایل Wrangler استفاده می‌کند و سایت اصلی را قبل از بسته‌بندی می‌سازد. ساخت پنل مستقل به‌تنهایی جای سایت اصلی منتشر نمی‌شود.

## مواردی که انتقال نمی‌دهد

- داده، حساب‌های پنل و تغییرات CMS روی D1 میزبانی Sites به‌صورت خودکار منتقل نمی‌شوند. در صورت نیاز باید جداگانه و خصوصی منتقل شوند.
- کاربر، حسابداری، اشتراک و ایجنت Convex قبلی همچنان به همان سرور قبلی وابسته‌اند.
- پیامک، درگاه پرداخت و فعال‌سازی خودکار اشتراک متصل نمی‌شوند. خرید یک‌ماههٔ ۵۰۰ هزار تومانی همچنان از تلگرام `@Cafenetyarr` انجام می‌شود.

انتشار روی Cloudflare فقط پس از اتصال حساب و موفقیت Deploy واقعی است. اضافه‌شدن این فایل‌ها به گیت‌هاب به‌معنی ایجاد Worker در حساب شما نیست.

## بررسی انجام‌شده

بسته با Wrangler رسمی نسخهٔ `4.164.0` در حالت `--dry-run` ساخته شد؛ Worker حدود ۱٫۳۲ مگابایت با فشرده‌سازی gzip است و اتصال `DB` شناخته شد. ۱۲ آزمون اعتبارسنجی هویت Access شامل امضا، Audience، صادرکننده، انقضا و رد هدر جعلی موفق بودند. این بررسی به حساب Cloudflare متصل نشده، دیتابیس واقعی نساخته و ورود زندهٔ Access را آزمایش نکرده است.
