# پشتیبان‌گیری و بازیابی

این سند رویه پیشنهادی برای محیط Production است. هیچ نسخه‌ای از آن به‌تنهایی اثبات نمی‌کند که پشتیبان‌گیری خودکار یا بازیابی واقعی انجام شده است؛ نتیجه هر اجرا باید ثبت شود.

## ۱. دامنه پشتیبان

- **دیتابیس Convex:** همه جدول‌ها، از جمله کاربران، کافی‌نت‌ها، تراکنش‌های دفتر مالی، اشتراک‌ها، پرداخت‌ها، تیکت‌ها و audit log.
- **فایل‌های Storage:** لوگو و پیوست‌ها؛ فقط با `--include-file-storage` در export قرار می‌گیرند.
- **کد Frontend/Backend:** تاریخ Git و commit مرجع، نه کپی دستی فایل‌ها.
- **کلیدها و رمزها:** در export معمولاً مقدارهای محیطی وجود ندارند. آن‌ها باید در password manager یا secret store جدا نگهداری شوند. فایل `.env` را در پشتیبان عمومی قرار ندهید.
- **حساب سرویس‌های خارجی:** مدارک دسترسی، وضعیت پلن و روش بازیابی باید در سند عملیات جدا ثبت شود.

## ۲. پشتیبان دستی

```bash
mkdir -p backups
bunx convex export --prod --include-file-storage \
  --path "backups/prod-$(date -u +%Y%m%d-%H%M%S).zip"
sha256sum backups/prod-*.zip
unzip -tqq backups/prod-YYYYMMDD-HHMMSS.zip
```

پوشه `backups/` در `.gitignore` است. فایل پشتیبان شامل داده شخصی و هش رمز است؛ دسترسی آن را محدود کنید و در Git یا فضای عمومی نگذارید.

## ۳. پشتیبان روزانه خودکار

اسکریپت `scripts/backup.sh` این مراحل را انجام می‌دهد:

1. export تولید با فایل‌های Storage؛
2. بررسی اینکه فایل خالی نیست؛
3. تست سالم بودن zip با `unzip -t`؛
4. ساخت checksum SHA-256؛
5. کپی اختیاری خارج از سرور با `rclone` در صورت تنظیم `BACKUP_REMOTE`؛
6. نگهداری محلی ۳۰ روزه (قابل تغییر با `RETENTION_DAYS`).

```bash
CONVEX_DEPLOY_KEY=... BACKUP_DIR=backups ./scripts/backup.sh
```

برای کپی خارج از سرور:

```bash
BACKUP_REMOTE=remote:kafinetyar/prod ./scripts/backup.sh
```

نام remote و کلید rclone را در محیط امن runner تنظیم کنید، نه در سند یا repository.

### GitHub Actions

فایل `.github/workflows/backup.yml` هر روز ساعت **۰۲:۳۰ UTC** اجرا می‌شود و با `workflow_dispatch` هم قابل اجرای دستی است.

پیش‌نیازها:

1. secret با نام `CONVEX_DEPLOY_KEY` برای deployment تولید.
2. فعال بودن Actions و دسترسی به artifactها.
3. بررسی دوره‌ای وضعیت اجرا؛ شکست workflow باید به مالک پاسخ‌گو اطلاع داده شود. GitHub ممکن است فقط برای watcherها ایمیل بفرستد؛ به هشدار پیش‌فرض اکتفا نکنید.
4. artifact پیش‌فرض ۳۰ روز نگهداری می‌شود. برای نگهداری بلندمدت، `BACKUP_REMOTE` و rclone را روی runner امن تنظیم کنید یا artifact را به storage خارجی منتقل کنید.

> تا زمانی که secret تنظیم نشده باشد، workflow با شکست متوقف می‌شود. این رفتار عمدی است و نباید به‌عنوان پشتیبان موفق تلقی شود.

## ۴. بازیابی آزمایشی (Restore Drill)

بازیابی را اول روی یک deployment **staging تازه** انجام دهید:

```bash
unzip -tqq backups/prod-YYYYMMDD-HHMMSS.zip
ALLOW_PRODUCTION_RESTORE=NO \
  ./scripts/restore.sh backups/prod-YYYYMMDD-HHMMSS.zip <STAGING_DEPLOYMENT> --confirm
```

`--replace-all` همه جدول‌های مقصد را جایگزین می‌کند و برای staging تازه یا محیط بازیابی مناسب است. هرگز آن را روی production بدون تأیید صریح و export فوری اجرا نکنید.

پس از import، این موارد را بررسی کنید:

- [ ] ورود یک حساب تستی و بازیابی context کافی‌نت.
- [ ] تعداد کاربران، کافی‌نت‌ها، تراکنش‌های دفتر مالی و اشتراک‌ها با export مطابقت دارد.
- [ ] جداسازی دو کافی‌نت نمونه حفظ شده است.
- [ ] فایل لوگو و پیوست از Storage باز می‌شود.
- [ ] یک پرداخت/فاکتور تاریخی فقط خوانده می‌شود و وضعیت آن تغییر نکرده است.
- [ ] خبر، نرخ‌نامه، تیکت و اعلان‌ها قابل خواندن هستند.
- [ ] مسیر `/admin/health` و audit log داده دارد.
- [ ] login، dashboard، accounting و support smoke test می‌شوند.

نتیجه (تاریخ، اندازه، checksum، deployment مقصد، فرد اجراکننده و خطاها) را در گزارش عملیات ثبت کنید. **بازیابی واقعی در این نسخه انجام نشده است** و باید پیش از انتشار به‌صورت انسانی تکمیل شود.

## ۵. بازیابی Production

1. ترافیک ورودی را متوقف یا محدود کنید.
2. از وضعیت فعلی Production یک export فوری بگیرید؛ حتی اگر خراب به نظر می‌رسد.
3. تأیید انسانی مالک محصول و مسئول فنی را ثبت کنید.
4. frontend را به build سازگار با نسخه‌ای که restore می‌شود برگردانید.
5. با `ALLOW_PRODUCTION_RESTORE=YES` و deployment دقیق، بازیابی را اجرا کنید.
6. smoke checks و بررسی audit را انجام دهید.
7. حادثه، زمان شروع/پایان، داده از دست رفته و اقدام پیشگیرانه را ثبت کنید.

## ۶. اهداف پیشنهادی

| شاخص | هدف پیشنهادی | وضعیت فعلی |
| --- | --- | --- |
| RPO (بیشترین داده از دست رفته) | حداکثر ۲۴ ساعت | وابسته به اجرای موفق workflow |
| RTO (زمان تقریبی بازگشت) | حداکثر ۲ ساعت | تمرین نشده |
| نگهداری روزانه | ۳۰ روز | تنظیم اسکریپت |
| نگهداری بلندمدت | ۹۰ روز یا بیشتر خارج از GitHub | نیازمند storage خارجی |
| تست بازیابی | حداقل هر ۹۰ روز | انجام نشده |

این اهداف تعهد SLA نیستند و باید پس از انتخاب میزبان و سرویس پایش نهایی شوند.

## ۷. محدودیت‌ها

- export/import فقط با دسترسی معتبر Convex و deployment مقصد کار می‌کند.
- فایل‌های Storage بزرگ، زمان و فضای بیشتری مصرف می‌کنند.
- پشتیبان دیتابیس، تنظیمات DNS/SSL/میزبان یا secretهای محیط را بازیابی نمی‌کند.
- بررسی `unzip -t` فقط سالم بودن فایل را می‌سنجد و جای بازیابی واقعی را نمی‌گیرد.
- هیچ تضمینی برای تحویل alert شکست workflow بدون سرویس پایش خارجی وجود ندارد.
