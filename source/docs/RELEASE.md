# راهنمای انتشار کافی‌نت‌یار

این سند فقط دستورالعمل عملیاتی است و هیچ مقدار محرمانه‌ای در آن قرار ندارد. همه کلیدها باید در تنظیمات محیط (Keys/API keys یا محیط Convex) ثبت شوند، نه در Git.

مستندات مرتبط:

- [`docs/PRODUCTION.md`](./PRODUCTION.md): دامنه/SSL، Staging، Rollback، هزینه، پایش و Go/No-Go.
- [`docs/BACKUP.md`](./BACKUP.md): پشتیبان‌گیری روزانه، retention و بازیابی آزمایشی.
- [`docs/AUDIT-REPORT-11.md`](./AUDIT-REPORT-11.md): گزارش بازرسی مستقل، شواهد تست و آمادگی انتشار.
- [`CHANGELOG.md`](../CHANGELOG.md): دامنه تغییرات نسخه ۳٫۱٫۰.

> این سند و اسناد مرتبط، انجام انتشار واقعی یا بازیابی را اثبات نمی‌کنند. وضعیت فعلی **آماده انتشار مشروط** است؛ تا تکمیل موارد بخش ۱۰ سند Production، انتشار Production انجام نشود.

## ۱. متغیرهای محیطی

### کلاینت (Vite / میزبان Frontend)

| متغیر | الزامی | توضیح |
| --- | --- | --- |
| `VITE_CONVEX_URL` | بله | نشانی deployment Convex؛ باید هنگام build در دسترس باشد. |
| `VITE_VLY_APP_ID` | اختیاری | شناسه اپ برای ابزار پایش/پشتیبانی Freebuff. |
| `VITE_VLY_MONITORING_URL` | اختیاری | endpoint پایش سمت کلاینت در صورت فعال بودن. |

### بک‌اند (محیط Convex)

| متغیر | الزامی | توضیح |
| --- | --- | --- |
| `SITE_URL` | بله برای پرداخت | نشانی عمومی و HTTPS برنامه؛ مبنای callback زرین‌پال. |
| `VLY_APP_URL` | جایگزین | فقط اگر `SITE_URL` تنظیم نشده باشد استفاده می‌شود. |
| `ZARINPAL_MERCHANT_ID` | بله برای پرداخت واقعی | مرچنت زرین‌پال؛ بدون آن خرید اشتراک باید «نیازمند تنظیمات» بماند. |
| `SITE_ADMIN_BOOTSTRAP_PHONE` | بله فقط برای راه‌اندازی اولیه | شماره مالک/مسئول؛ فقط این حساب می‌تواند یک بار نقش مدیر اصلی را فعال کند. پس از فعال‌سازی حذف شود. |
| `VLY_INTEGRATION_KEY` | بله برای AI و ایمیل OTP | کلید درگاه یکپارچه‌سازی؛ فقط سمت سرور. |
| `VLY_INTEGRATION_BASE_URL` | اختیاری | پیش‌فرض درگاه؛ در صورت استفاده از محیط دیگر تغییر دهید. |
| `VLY_CONVEX_AUTH_ISSUER` | اختیاری | پیش‌فرض `https://freebuff.com`؛ برای federation خارجی. |
| `JWKS` و `JWT_PRIVATE_KEY` | بله | توسط Convex Auth استفاده می‌شوند؛ مقدارها را در محیط امن نگه دارید و هرگز در کد نگذارید. |
| `CONVEX_SITE_URL` | خودکار | توسط Convex تنظیم می‌شود؛ مبنای provider احراز هویت. |

`CONVEX_DEPLOYMENT` و `CONVEX_DEPLOY_KEY` فقط برای CLI/CI هستند و نباید در bundle کلاینت قرار بگیرند. کلیدها را از پنل Keys/API keys یا محیط میزبان تزریق کنید.

## ۲. پیش از انتشار

1. تأیید انسانی تغییرات و دامنه انتشار.
2. تهیه نسخه پشتیبان کامل از دیتابیس و فایل‌ها (بخش ۳).
3. تنظیم `SITE_ADMIN_BOOTSTRAP_PHONE` فقط برای اولین ورود و ثبت مالک مدیر اصلی؛ سپس حذف آن از محیط.
4. اجرای بررسی‌های محلی:
   ```bash
   bunx convex dev --once
   bunx tsc -b --noEmit
   bun run test
   bun run lint
   bun run build
   ```
5. ثبت خروجی checks و مقایسه با نسخه قبلی.
6. بررسی اینکه هیچ فایل `.env`، کلید یا مقدار محرمانه در تغییرات یا artifact وجود ندارد.
7. تعیین بازه نگهداری و مالک پاسخ‌گو برای rollback.

> مهاجرت مخرب یا `--replace-all` بدون پشتیبان و تأیید انسانی ممنوع است. تغییرات schema باید ابتدا روی staging و با نسخه پشتیبان آزمایش شوند.

## ۳. پشتیبان‌گیری و بازیابی

### پشتیبان کامل (دیتابیس + فایل‌ها)

```bash
mkdir -p backups
bunx convex export --prod --include-file-storage --path "backups/prod-$(date +%Y%m%d-%H%M%S).zip"
```

برای مسیر خودکار، بررسی zip و checksum از `./scripts/backup.sh` استفاده کنید. جزئیات و محدودیت‌ها در `docs/BACKUP.md` آمده است. workflow روزانه تا زمانی که `CONVEX_DEPLOY_KEY` تنظیم نشود ناموفق می‌ماند و نباید پشتیبان موفق تلقی شود.

برای dev از `--prod` استفاده نکنید. قبل از مهاجرت، خروجی را در محلی خارج از سرور تولید هم نگه دارید و checksum آن را ثبت کنید:

```bash
sha256sum backups/prod-*.zip
```

### بازیابی در یک deployment تازه

ابتدا deployment مقصد را جدا کنید (به‌ویژه staging). سپس:

```bash
bunx convex import --deployment <STAGING_DEPLOYMENT> --replace-all -y backups/prod-YYYYMMDD-HHMMSS.zip
```

`--replace-all` تمام جدول‌های موجود در مقصد را جایگزین می‌کند و فقط برای محیط بازیابی/تازه مجاز است. هرگز آن را روی production بدون تأیید صریح و پشتیبان تازه اجرا نکنید.

### بازیابی در production

1. نوشتن/توقف موقت ترافیک ورودی.
2. تهیه export فوری از وضعیت فعلی production.
3. اجرای import با `--replace-all -y` فقط پس از تأیید انسانی.
4. بازگرداندن frontend به build سازگار با schema بازیابی‌شده.
5. اجرای smoke checks بخش ۶.

Convex فایل‌های storage را در export با `--include-file-storage` شامل می‌کند؛ بدون آن، رکوردهای دارای `fileId` ممکن است به فایل در دسترس اشاره نکنند.

## ۴. استقرار staging

1. یک پروژه/دهپلویمنت جدا برای staging بسازید؛ داده production را مستقیم به staging کپی نکنید مگر داده ناشناس‌شده باشد.
2. کلیدهای staging را جدا تنظیم کنید. برای درگاه پرداخت از sandbox استفاده کنید و `ZARINPAL_MERCHANT_ID` واقعی production را در staging نگذارید.
3. بک‌اند staging را با deploy key مخصوص همان deployment منتشر کنید:
   ```bash
   CONVEX_DEPLOY_KEY=<STAGING_DEPLOY_KEY> bunx convex deploy --cmd "bun run build" --cmd-url-env-var-name VITE_CONVEX_URL
   ```
   مقدار key را در CI secret store نگه دارید و در shell history یا سند ننویسید.
4. خروجی `dist/` را روی میزبان staging منتشر کنید و `VITE_CONVEX_URL` همان staging را تأیید کنید.
5. یک حساب آزمایشی جدید بسازید، کافی‌نت ایجاد کنید و سناریوهای بخش ۶ را اجرا کنید.
6. داده‌های تست را با شناسه مشخص (مثلاً شماره‌های ۰۹۱۲۰۰۰۰۰xx) بسازید و در پایان پاک‌سازی کنید.

## ۵. استقرار production

1. تأیید انسانی نسخه، checks و پشتیبان.
2. تنظیم متغیرهای production در محیط Convex و میزبان frontend.
3. انتشار بک‌اند:
   ```bash
   bunx convex deploy --cmd-url-env-var-name VITE_CONVEX_URL --cmd "bun run build"
   ```
   این دستور طبق CLI به deployment پیش‌فرض production اشاره می‌کند؛ پیش از اجرا مقصد را دوباره بررسی کنید.
4. انتشار artifact نهایی frontend از پوشه `dist` روی میزبان production.
5. بررسی HTTPS، دامنه، callback پرداخت و CORS/مجوزهای میزبان.
6. فعال‌سازی پایش و ثبت release/زمان/commit مرجع در گزارش عملیات.

در محیط Freebuff، انتشار و کلیدها از طریق کنترل‌های پلتفرم مدیریت می‌شوند؛ از اجرای دستی dev server یا تغییر تنظیمات Vite/HMR خودداری کنید.

## ۶. بررسی پس از انتشار (Smoke Checks)

- [ ] صفحه `/` باز می‌شود و CTAها به `/auth` می‌روند.
- [ ] ثبت‌نام/ورود با شماره و رمز کار می‌کند؛ خروج نشست را می‌بندد.
- [ ] فقط شماره `SITE_ADMIN_BOOTSTRAP_PHONE` می‌تواند یک بار مدیر اصلی را فعال کند و پس از فعال‌سازی، حساب دیگری موفق نمی‌شود.
- [ ] بازیابی رمز با کد/OTP واقعی کار می‌کند (در صورت فعال بودن سرویس ایمیل).
- [ ] ایجاد کافی‌نت، ویرایش اطلاعات و آپلود لوگو کار می‌کند.
- [ ] افزودن کارمند و ورود او با نقش محدود کار می‌کند.
- [ ] دو کافی‌نت مستقل نمی‌توانند داده مالی، کارمند، تیکت یا گفت‌وگوی هم را ببینند.
- [ ] اخبار منتشرشده دیده می‌شوند و خبر زمان‌بندی‌شده/پیش‌نویس به کاربر عادی نمایش داده نمی‌شود.
- [ ] بانک سایت‌ها، علاقه‌مندی و پیشنهاد سایت کار می‌کنند و لینک خراب مدیریت می‌شود.
- [ ] نرخ‌نامه از دیتابیس خوانده می‌شود؛ نرخ بدون تأیید مبلغ نشان نمی‌دهد.
- [ ] دستیار با منبع پاسخ می‌دهد و در نبود منبع، ادعای قطعی نمی‌کند.
- [ ] خرید اشتراک با sandbox/آزمایشی درگاه بررسی شده و تأیید فقط سمت سرور است؛ پرداخت تکراری ثبت نمی‌شود.
- [ ] فاکتور، تمدید، انقضا و کد تخفیف درست رفتار می‌کنند.
- [ ] نقش‌های مدیر فقط بخش‌های مجاز را می‌بینند و عملیات حساس در audit ثبت می‌شود.
- [ ] صفحات در موبایل، تبلت و دسکتاپ بدون overflow و با RTL درست نمایش داده می‌شوند.
- [ ] حالت روشن/تاریک و کنتراست متن‌های اصلی قابل قبول است.
- [ ] خطای شبکه/قطع سرویس پیام قابل فهم می‌دهد و صفحه سفید نمی‌شود.
- [ ] لاگ‌های Convex و frontend را بررسی کنید؛ خطای جدید یا افشای secret نباید وجود داشته باشد.

## ۷. پایش، خطا و پاسخ به حادثه

- **Convex:** Dashboard → Logs و Functions؛ خطاهای mutation/action و latency را بررسی کنید. برای خطاهای تکراری alert بسازید.
- **Frontend:** خطاهای runtime، خطای chunk load و درخواست‌های ناموفق را در سرویس پایش (در صورت فعال بودن `VITE_VLY_MONITORING_URL`) دنبال کنید.
- **پرداخت:** وضعیت سفارش‌های `pending` و callbackهای ناموفق را روزانه بررسی کنید؛ تطبیق پرداخت فقط با داده سمت سرور.
- **امنیت:** audit log مدیران، تلاش‌های ورود، نرخ خطای OTP و دسترسی‌های غیرمجاز را پایش کنید.
- **بازگشت (Rollback):** ابتدا ترافیک را متوقف/محدود کنید، export فوری بگیرید، frontend را به build قبلی برگردانید و در صورت نیاز دیتابیس را طبق `docs/BACKUP.md` بازیابی کنید. تغییر schema را بدون بررسی سازگاری به عقب برنگردانید.
- **اطلاع‌رسانی:** در حادثه امنیتی، دسترسی‌های مشکوک را ببندید، کلیدهای در معرض را rotate کنید و کاربران متأثر را طبق رویه اطلاع‌رسانی کنید.

## ۸. محدودیت‌های شناخته‌شده انتشار

- بدون `ZARINPAL_MERCHANT_ID` و `SITE_URL`، پرداخت واقعی آزمایش‌شده نیست و نباید موفق نمایش داده شود.
- بدون `VLY_INTEGRATION_KEY`، AI و ایمیل OTP کار نمی‌کنند.
- ایمیل و پیامک واقعی خارج از درگاه موجود و alerting خارجی در این نسخه پیکربندی نشده‌اند.
- workflow پشتیبان‌گیری خودکار اضافه شده، اما اجرای موفق آن و بازیابی واقعی تأیید نشده است.
- دفتر مالی ماندگار است؛ با این حال داده واردشده توسط کاربر جایگزین حسابرسی رسمی یا تأیید حقوقی نیست.
- تست مرورگری خودکار (Playwright) و تست چهار اندازه روی دستگاه واقعی در این دور انجام نشده است؛ پیش از انتشار باید توسط انسان تکمیل شود.
- دامنه، DNS، SSL، staging جدا و میزبان Production در این دور پیکربندی نشده‌اند.
- برخی فهرست‌های مدیریتی برای حجم بزرگ داده صفحه‌بندی سمت سرور ندارند؛ قبل از رشد زیاد داده، pagination اضافه شود.
- متن صفحات حقوقی پیش‌نویس است و تأیید مشاور حقوقی ندارد.
