# راهنمای Production کافی‌نت‌یار

آخرین به‌روزرسانی: ۹ نوامبر ۲۰۲۶ · نسخه محصول: **۳٫۱٫۰**

> **وضعیت: آماده انتشار مشروط.** هسته بک‌اند با تست تأیید شده، اما دامنه، SSL، میزبان Production، پرداخت واقعی، مرورگر/E2E و بازیابی آزمایشی هنوز پیکربندی یا تأیید نشده‌اند. هیچ سرویس پولی یا دامنه‌ای در این مرحله خریداری نشده است.

## ۱. معماری فعلی

- **Frontend:** Vite + React 19 + TypeScript، خروجی `dist/` و مسیرهای React Router.
- **Backend/DB:** Convex و Convex Auth؛ توابع در `src/convex/`.
- **Storage:** Convex File Storage برای لوگو و پیوست‌ها.
- **پرداخت:** زرین‌پال؛ تا نبود `ZARINPAL_MERCHANT_ID` و `SITE_URL` پرداخت واقعی غیرفعال/نیازمند تنظیمات است.
- **هوش مصنوعی و OTP:** از طریق `VLY_INTEGRATION_KEY`؛ بدون کلید، مسیرهای واقعی باید محدود بمانند.
- **محیط توسعه فعلی:** یک deployment توسعه Convex و preview پلتفرم؛ این محیط Production نیست.

Development و Production باید deployment، کلیدها، دامنه و داده جدا داشته باشند. هیچ داده نمونه یا حساب مهمان نباید برای پوشش کمبود داده Production استفاده شود.

## ۲. متغیرهای محیطی

### Frontend (build-time)

| متغیر | Production | یادداشت |
| --- | --- | --- |
| `VITE_CONVEX_URL` | الزامی | باید URL deployment تولید باشد، نه dev. |
| `VITE_VLY_APP_ID` | اختیاری | فقط اگر پایش Freebuff فعال است. |
| `VITE_VLY_MONITORING_URL` | اختیاری | endpoint پایش کلاینت. |

### Convex (server-side)

| متغیر | Production | یادداشت |
| --- | --- | --- |
| `SITE_URL` | الزامی برای پرداخت و auth | دامنه canonical با HTTPS. |
| `VLY_APP_URL` | جایگزین | فقط اگر `SITE_URL` تنظیم نشده باشد. |
| `ZARINPAL_MERCHANT_ID` | الزامی برای پرداخت واقعی | فقط سمت سرور. |
| `SITE_ADMIN_BOOTSTRAP_PHONE` | الزامی فقط برای راه‌اندازی اولیه | شماره موبایل مالک/مسئول که فقط او می‌تواند یک بار نقش مدیر اصلی را فعال کند. پس از فعال‌سازی می‌توان آن را حذف کرد. |
| `VLY_INTEGRATION_KEY` | الزامی برای AI/OTP واقعی | فقط سمت سرور. |
| `VLY_INTEGRATION_BASE_URL` | اختیاری | فقط در صورت تغییر درگاه. |
| `VLY_CONVEX_AUTH_ISSUER` | اختیاری | پیش‌فرض پلتفرم. |
| `JWKS` / `JWT_PRIVATE_KEY` | الزامی | توسط Convex Auth؛ در secret store. |
| `CONVEX_SITE_URL` | خودکار | توسط Convex تنظیم می‌شود. |
| `SEED_DEMO_DATA` | اختیاری | فقط در Development مقدار `true` بگیرد. در Production تنظیم نشود. |
| `BACKUP_REMOTE` | توصیه‌شده | مسیر rclone برای نسخه خارج از سرور. |

`CONVEX_DEPLOY_KEY` فقط در CI/CLI استفاده شود و هرگز در bundle کلاینت، Git یا سند قرار نگیرد.

## ۳. دامنه، DNS و SSL

هیچ دامنه‌ای خریده یا به سرویس فعلی متصل نشده است. برای Production:

1. دامنه رسمی را با مالکیت کاربر و تأیید او ثبت کنید. نام دامنه باید از سوی مالک محصول انتخاب شود؛ این سند نامی را از پیش تعیین نمی‌کند.
2. DNS را در registrar یا سرویس DNS معتبر مدیریت کنید. رکورد `A`/`AAAA` یا `CNAME` را دقیقاً مطابق میزبان frontend تنظیم کنید.
3. برای دامنه اصلی و `www` تصمیم بگیرید؛ یکی را canonical کنید و دیگری را با redirect دائمی به آن برگردانید.
4. SSL را از میزبان یا CDN با گواهی معتبر و تمدید خودکار فعال کنید. HTTP باید به HTTPS redirect شود.
5. `SITE_URL` را دقیقاً روی دامنه canonical با `https://` تنظیم کنید. callback زرین‌پال باید به همین origin برگردد.
6. `www`، apex، callback و مسیرهای auth را از خارج شبکه تست کنید. گواهی منقضی، mixed content و redirect loop نباید وجود داشته باشد.
7. CORS و allowed origins را در میزبان frontend، auth و درگاه پرداخت بررسی کنید. تنظیم CORS فقط با wildcard در Production مجاز نیست.
8. پس از اتصال، SPF/DKIM/DMARC ایمیل و کلیدهای سرویس‌های خارجی را جدا تنظیم و مستند کنید.

**وضعیت:** انجام نشده؛ دامنه و SSL تأیید نشده‌اند.

## ۴. Staging

Staging باید حداقل شامل این موارد باشد:

- deployment جداگانه Convex با داده ناشناس‌شده یا مصنوعی؛
- frontend جداگانه روی دامنه/ساب‌دامنه staging؛
- `CONVEX_DEPLOY_KEY` و کلیدهای جدا؛
- درگاه پرداخت sandbox و عدم استفاده از مرچنت Production؛
- حساب‌های تست با شماره‌های مشخص که در پایان پاک می‌شوند؛
- اجرای migration/schema جدید ابتدا در staging؛
- اجرای smoke checks و restore drill.

هیچ داده Production بدون ناشناس‌سازی به staging کپی نشود.

## ۵. مراحل استقرار

1. تأیید انسانی نسخه و commit مرجع.
2. ثبت پشتیبان Production و checksum آن.
3. اجرای `bunx convex dev --once` فقط برای codegen محلی؛ این دستور انتشار Production نیست.
4. اجرای `bunx tsc -b --noEmit`، `bun run test`، `bun run lint` و `bun run build`.
5. تنظیم secretها در محیط Production؛ هرگز در فایل قابل commit.
6. انتشار backend با دستور مجاز Convex و deployment تولید:
   ```bash
   bunx convex deploy --cmd-url-env-var-name VITE_CONVEX_URL --cmd "bun run build"
   ```
7. انتشار `dist/` روی میزبان Production.
8. اجرای smoke checks و بررسی logها.
9. فعال‌سازی پایش و ثبت release.

در محیط Freebuff، انتشار و کلیدها از کنترل‌های پلتفرم مدیریت می‌شوند. dev server یا تنظیمات HMR را دستی تغییر ندهید. این مراحل در این نسخه اجرا نشده‌اند.

## ۶. Rollback

### Frontend

آخرین artifact سالم را روی میزبان برگردانید. اگر asset hash عوض شده، cache/CDN را purge کنید و بررسی کنید که نسخه قدیمی با backend جدید سازگار است.

### Backend / دیتابیس

- تغییرات سازگار با نسخه قبل: فقط backend را به deployment قبلی برگردانید.
- تغییر schema ناسازگار: ترافیک را محدود کنید، export فوری بگیرید و طبق `docs/BACKUP.md` بازیابی کنید.
- `--replace-all` بدون export تازه، تأیید مالک و پنجره اعلام‌شده ممنوع است.
- بازگرداندن frontend بدون بررسی سازگاری schema می‌تواند داده را ناسازگار کند.

### معیار توقف

خطای ورود گسترده، نشت داده بین tenantها، پرداخت تکراری/نادرست، از دست رفتن دفتر مالی یا خطای migrate = توقف انتشار و rollback.

## ۷. پایش و نگهداری

**موجود در محصول:**

- صفحه `/admin/health` برای snapshot دیتابیس، کافی‌نت‌ها، تیکت‌ها، سفارش‌های پرداخت، مصرف ایجنت، آخرین audit و وضعیت پیکربندی.
- اعلان‌های درون‌برنامه‌ای برای پاسخ پشتیبانی، پرداخت موفق و نزدیک شدن انقضای اشتراک.
- audit log برای عملیات حساس مدیریتی.
- روزنامه پشتیبان‌گیری: `docs/BACKUP.md`.

**هنوز لازم است:**

- اتصال uptime/alerting خارجی و تعیین مالک پاسخ‌گو؛ هیچ سرویس پولی فعال نشده است.
- بررسی روزانه خطاهای Convex و frontend.
- بررسی هفتگی سفارش‌های `pending`/`failed` و تطبیق پرداخت.
- بازبینی دسترسی مدیران و audit.
- تست restore در staging حداقل هر ۹۰ روز.
- ثبت نسخه، commit، زمان release و نتیجه smoke checks.

## ۸. هزینه‌ها (تخمین، نه خرید)

| قلم | برآورد | وضعیت |
| --- | --- | --- |
| دامنه | حدود ۰٫۵ تا ۲ میلیون تومان در سال، بسته به TLD | خریداری نشده |
| میزبان Frontend | از رایگان تا چند میلیون تومان در ماه | انتخاب نشده |
| Convex | پلن رایگان توسعه؛ Production وابسته به مصرف | ارتقا داده نشده |
| ایمیل/پیامک | بر اساس تعداد پیام و ارائه‌دهنده | متصل نشده |
| پایش/Alerting | پلن رایگان یا اشتراک ماهانه | فعال نشده |
| درگاه پرداخت | کارمزد طبق قرارداد زرین‌پال | قرارداد واقعی تأیید نشده |

هیچ پرداخت، خرید دامنه یا فعال‌سازی سرویس پولی انجام نشده است. قیمت‌ها فقط برای برنامه‌ریزی‌اند و باید پیش از خرید از منبع رسمی بررسی شوند.

## ۹. جداسازی داده نمونه

- ثبت‌نام و ساخت کافی‌نت دیگر خبر Demo نمی‌سازد مگر `SEED_DEMO_DATA=true` در Development.
- درج و حذف داده نمونه از پنل مدیر همچنان دستی و صریح است.
- حساب مهمان از ورود عمومی حذف شده است؛ provider پشت صحنه برای سازگاری حفظ می‌شود اما مسیر محصول به آن وابسته نیست.
- داده نمونه موجود در deployment توسعه باید قبل از استفاده Production پاک یا در محیط جدا نگهداری شود. حذف خودکار داده توسعه انجام نشده است.
